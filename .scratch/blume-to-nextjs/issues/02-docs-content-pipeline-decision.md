# Docs content pipeline decision

Type: grilling
Status: resolved
Blocked by: 01

## Question

With the ecosystem facts in hand from `01-nextjs-mdx-pipeline-options`, choose
the hand-rolled docs pipeline. This is the spine of the migration: the sidebar,
the search palette, the agent-facing Markdown and prev/next all read from
whatever this decision produces.

Settle:

1. **How MDX becomes a page.** File-based MDX routes, or a single
   `app/docs/[[...slug]]/page.tsx` that loads and compiles content from
   `apps/web/docs/`? The `/docs` base path and the existing file layout
   (`docs/index.mdx`, `docs/installation.mdx`, `docs/theming.mdx`,
   `docs/components/*.mdx` — 65 of them) map to URLs that are frozen, so the
   routing shape must reproduce them exactly.
2. **The content index.** What is generated, when, and in what form? It must
   carry at minimum: route, title, description, heading tree, and a handle on
   the raw MDX body. Generated by a build script into a checked-in-or-not JSON,
   by a content layer, or derived at request time.
3. **Is the index typed**, and is a missing or malformed frontmatter field a
   build error? (Blume's content collection schema enforces this today.)
4. **Where do frontmatter fields live?** Confirm the real field set across all
   68 files, not just `title`/`description`.
5. **The remark/rehype chain.** Fix the ordered list: frontmatter, heading
   slugs, TOC extraction, Shiki (see `05-code-highlighting-parity`), external
   link `rel`, and anything `04-mdx-content-component-parity-set` needs.
6. **Dev-time behaviour.** Editing a `.mdx` file should reflect without a manual
   step. If the chosen shape needs a generate step, what watches it?
7. **Build time.** 68 MDX pages plus 137 highlighted demo sources plus 68 OG
   images. Is there a number beyond which the shape is wrong?
8. **Prev/next and the TOC** — do they come from the index (ordering from
   `03-sidebar-and-nav-source-of-truth`) or from the file tree?

## Added requirement (from `01-nextjs-mdx-pipeline-options`)

**Heading anchor IDs are a frozen contract and they will drift by default.**
`rehype-slug` slugs through `github-slugger`; Blume uses its own Unicode-class
`slugify`, deliberately matched to its renderer. Heading anchors are published
deep links (every `#section` link into the docs, internal and external).

So the remark/rehype chain in question 5 has a hard requirement: reproduce
Blume's slug algorithm exactly, by porting it, not by picking a slugger that
looks close. `13-parity-proof-method` gates on it.

## Answer

Resolved 2026-09-19 with the dev, over two grilling rounds.

### Corrections to the question, established before deciding

**Q4 was not a question — it is a measured fact.** Frontmatter is exactly
`title` + `description` on all 68 files, no other key anywhere (already measured
by `01-nextjs-mdx-pipeline-options`, re-confirmed here).

**The `## Added requirement` above is refuted. Heading anchor IDs do not
drift.** `01` reported that Blume slugs headings with its own Unicode-class
`slugify`. It does not. That `slugify` (`blume/src/core/sources/normalize.ts`)
is for *route* slugs and for the OpenAPI/Sanity/Notion sources, none of which
this site uses. Heading anchors come from `blume/src/markdown/heading-anchors.ts`,
which uses **`github-slugger`** — the same library `rehype-slug` uses — and
`extractHeadings` uses the same slugger, with a source comment that explicitly
justifies choosing it over a hand-rolled slugify.

Verified against the live site:

| Heading | Live `id` | What it proves |
| --- | --- | --- |
| `ContextMenuCheckboxItem and ContextMenuRadioGroup / ContextMenuRadioItem` | `...radiogroup--contextmenuradioitem` | double hyphen preserved — not a hand-rolled slugify |
| `Detached triggers (createHandle)` | `detached-triggers-createhandle` | github-slugger punctuation handling |
| `Examples` x2 in `toggle.mdx` | `examples`, `examples-1` | same duplicate disambiguation |

Corpus facts that make this safe: **no `# ` (h1) in any of the 68 files**, and
exactly **one** duplicate heading text in the whole corpus (`toggle.mdx` →
"Examples"). The page title `<h1>` carries **no `id`** and does **not** advance
the slugger — confirmed live: `toggle.mdx`'s `### Toggle` is `id="toggle"`, not
`toggle-1`. So `rehype-slug` over the MDX body alone reproduces every published
anchor exactly.

Consequence: porting a slug algorithm is **not** a requirement. It becomes a
smoke test. `13-parity-proof-method` keeps the anchor-ID diff as a gate (cheap,
and it catches an accidental slugger swap), but its stated reason is wrong and
is corrected there.

### Additional corpus measurements taken for this decision

- **Tables in 57 of 68 files** → `remark-gfm` is required.
- **Zero** strikethrough, task lists, footnotes, HTML comments.
- **Zero** headings containing a link → `rehype-autolink-headings` needs no
  function-valued `test`.
- **5 absolute `https://sevenui.dev` markdown links** in 2 files (`index.mdx`
  x2, `installation.mdx` x3). Two further `sevenui.dev` occurrences are inside
  code fences / inline code and are not links.
- Prev/next today follows the **flattened sidebar order**, not the file tree —
  confirmed live: `/docs/theming` → next `/docs/components/accordion`.
- TOC today is **h2 + h3** (`padding-inline-start` 0 / 0.75rem), rendered twice
  (sticky right rail + mobile `<details>`), scroll-spied by a `<blume-toc>`
  custom element writing `aria-current="location"`.
- The `.md` endpoint is the **raw MDX**: frontmatter verbatim, `<Component>`
  expanded to a fenced source block, `<InstallCommand>` left unserialized (the
  known bug). So the index must carry the raw body, not only compiled output.

### The decisions

**1. Routing — catch-all + dynamic import.** One
`app/docs/[[...slug]]/page.tsx` with `generateStaticParams`, loading content
from `apps/web/docs/` by dynamic import. The authored content tree stays where
it is. Rejected: route-file MDX (would move 68 files into `app/`, cannot serve
the `.md` endpoints from the same source, and forces shared layout data through
per-file exports) and `next-mdx-remote-client/rsc` (its only advantage was
`vfile.data.toc`, which decision 8 makes unnecessary).

**`basePath` in `next.config` is not used.** It shifts the entire site; only the
docs section lives under `/docs`. `/docs` is a folder. (Consistent with
`12-chrome-port-client-and-server-boundaries` question 5.)

**2. Content index — no codegen.** A server-only module under `lib/docs/`
reading the filesystem with `vfile-matter` (~60 lines, the shape Blume's own
`discoverContent` already has). Record:
`{ route, title, description, headings[], sourcePath, raw }`. Every consumer
(page render, `generateStaticParams`, sitemap, `llms.txt`, the `.md` endpoints,
search-index generation, prev/next) runs at build time on the server. Rejected:
a checked-in JSON (a drifting artifact plus a watcher debt) and a content layer
(`velite` is broken under Turbopack on a vendored Zod v3; `content-collections`
routes MDX through `mdx-bundler` + `esbuild`).

**Vocabulary.** The **content index** (68 docs pages) is a distinct thing from
the **example index** (137 demos, owned by
`06-inline-demo-rendering-contract`). Keep the names apart.

**3. Typed and validated — yes, with zod.** A `DocPage` type and a zod schema;
missing or malformed frontmatter **fails the build**, as Blume's content
collection schema does today. `description` feeds both `<meta>` and the OG
image, so a silent empty string is a production regression. zod is taken as a
dependency deliberately — the dev expects to need it elsewhere in `apps/web`.

**4. The remark/rehype chain — this order, locked.**

```
remark:  remark-frontmatter(['yaml'])  ->  remark-gfm
rehype:  rehype-slug  ->  rehype-autolink-headings(wrap)  ->  @shikijs/rehype  ->  rehype-external-links
```

`rehype-slug` must precede `rehype-autolink-headings` (it writes the `id` the
anchor links to). Shiki emits no `<a>`, so its position relative to the link
plugins is free; `rehype-external-links` runs last, and the `href="#..."`
anchors it then sees are protocol-less and untouched. The TOC is **not** in the
chain (decision 8). Element overrides are **not** in the chain — they are a
plain object passed at render time. `remark-mdx-frontmatter` is not needed:
`title`/`description` come from the index, and the chain's only frontmatter job
is stripping it from the output.

Every option in this chain is plain data, so the Turbopack loader-option
constraint from `01` is satisfied without an escape hatch.

**5. Shiki — `@shikijs/rehype` in the chain, two highlighter instances.** Plain
options (`themes: { light: 'github-light', dark: 'github-dark' }`,
`defaultColor: false`). A highlighter *instance* is not JSON-serializable, so
the loader cannot share the one used for demo sources, `InstallCommand` and the
gallery cards. Two instances, both on the 4-grammar fine-grained bundle (287 KB)
and the same theme pair; `05-code-highlighting-parity` measured the cost of not
reusing at ~160 ms per build.

Rejected: a local wrapper module sharing one highlighter (`01`'s escape hatch is
unverified — not something to hang the spine on), and dropping the fence plugin
entirely in favour of an async RSC `pre`/`code` override. The latter is
genuinely attractive — it would collapse the two code paths and erase the five
class-name differences `05` found — and `05`'s "no fence meta anywhere" finding
makes it technically safe. It was rejected only because it moves highlighting
from compile time to render time, losing Turbopack's per-file loader cache.
**It is the recorded fallback if `@shikijs/rehype` misbehaves under Turbopack.**

**6. External links — fix the content, delete the post-build pass.** The 5
absolute `https://sevenui.dev` markdown links are rewritten root-relative
(`/components`, `/blocks`). `rehype-external-links` then needs no
function-valued `test` and runs on plain options (`target: '_blank'`,
`rel: ['noopener', 'noreferrer']`), and the `astro:build:done` regex pass in
`blume.config.ts` dies with Blume. Those links were a content defect anyway —
absolute URLs to same-origin pages.

**7. No `blume-*` class names, and no replacement names either — Tailwind
utilities.** The two rendered-DOM hooks become inline utility classes. Both are
expressible as plain data (`properties.className` is a string array; the table
wrapper is a JSX `className`), so neither breaks the Turbopack constraint.

| Blume CSS today | Replacement |
| --- | --- |
| `.blume-heading-anchor`: `color/font-weight: inherit`, `text-decoration: none`, `::after { content: "#"; color: muted-foreground; margin-inline-start: .35em; opacity 0 -> 1 on hover/focus-visible, .15s }` | `text-inherit font-inherit no-underline after:content-['#'] after:ms-[0.35em] after:text-muted-foreground after:opacity-0 after:transition-opacity after:duration-150 hover:after:opacity-100 focus-visible:after:opacity-100` |
| `.blume-table-scroll`: `overflow-x: auto`, `margin: 1.5rem 0`, `1px border`, `radius`, `> table { margin: 0 }`, `th { white-space: nowrap }`, `:is(th, td) { padding: .5rem .75rem }` | `my-6 overflow-x-auto rounded-blume border border-border [&>table]:m-0 [&_th]:whitespace-nowrap [&_th]:px-3 [&_th]:py-2 [&_td]:px-3 [&_td]:py-2` |

Note: the `:is(th, td)` selector exists only to out-specify Blume Typography's
`:where()`-scoped rules. With `.prose` gone that specificity war disappears, so
this choice simplifies the CSS rather than carrying it over. The table wrapper
is produced by a `table` element override, not a rehype plugin — handed to
`04-mdx-content-component-parity-set`.

**8. Prev/next from the nav tree; TOC from the index.** Prev/next reads the nav
tree that `03-sidebar-and-nav-source-of-truth` produces, because that is what
ships today and the file tree cannot express the "Primitives" group. The TOC
comes from the index's **text scan** of the raw MDX (Blume's `extractHeadings`
shape), not from compiled output: `vfile.data` is unreachable through
`@next/mdx`, the same scan already feeds search and link validation, and it
keeps the TOC out of the RSC payload path. Depth is fixed at **h2 + h3**. The
text scan is safe here because no file contains an h1 and every heading is
literal text — no `{frontmatter.title}` interpolation, no JSX-produced headings.

**9. Dev-time — no watcher, no generate step.** Editing an `.mdx` body is
handled by Turbopack HMR on the imported module. Frontmatter and the heading
tree come from the index, so the index is **memoized in production and re-read
per request in dev** (reading 68 frontmatter blocks is a few ms). A new file is
picked up because the catch-all matches any slug and the index re-reads; a
deleted file 404s from the index.

**10. Build time — no gate, one recorded number, one binding rule.** Measure the
current `blume build` once before cutover and record it in the spec. The Next
build may be slower; a **>3x regression is a signal the shape is wrong**, not a
failing gate (the performance budget stays outside the cutover gate per
`13-parity-proof-method`). One rule is binding, because `05` showed payload and
repeated work are the real risks: **highlight each unique source once and
memoize it for the whole build** — the 137 demo sources recur across pages.

### Hand-offs

- **To `13-parity-proof-method`:** two new declared intended diffs — 5 changed
  `href` attributes (decision 6) and the two class-name sets (decision 7). Also:
  its stated reason for the anchor-ID gate is wrong; the gate stays, the reason
  is corrected.
- **To `01-nextjs-mdx-pipeline-options`:** a correction note on the slug claim.
- **To `01`'s smoke-test list:** verify that a template-literal
  `import(\`../../docs/${path}.mdx\`)` produces a Turbopack context module
  covering **nested** directories (`components/button`). If it does not, the
  import expression changes, not decision 1.
- **To `04-mdx-content-component-parity-set`:** the `table` element override
  produces the scroll wrapper (decision 7).
- **To `06` and `08`:** the example index and the search index are theirs; this
  ticket's index is the content index only.
